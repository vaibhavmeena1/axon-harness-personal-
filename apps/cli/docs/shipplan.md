# Axon CLI shipping and update runbook

This document describes the **implemented** Apple Silicon CLI distribution path. For operator commands and installation details, see [CLI README](../README.md#releasing); for backend settings, see [backend CLI releases](../../backend/README.md#cli-releases-macos-arm64-only). The [controlled-rollout proposal](plans/controlled-rollout-versioning-updates.md) is separate from current behavior.

## What ships

- `axon` is a Bun-compiled, native `darwin-arm64` launcher installed at `${AXON_HOME:-$HOME/.axon}/bin/axon`. macOS arm64 is the supported release target; the installer rejects other platforms and obvious containers. The binary does **not** bundle Pi or require Bun on end-user machines. Pi bootstrap **does** require Node.js 22.19+ and npm; the installer checks for them and can offer a Homebrew install/upgrade in an interactive terminal.
- The only supported harness is `pi`. `axon pi [arguments...]` dispatches before Commander, preserves user argument order and inherited stdio/cwd, and returns Pi's exit code or signal outcome. Launcher-owned commands are `--version`, `auth login [--browser]`, `auth status`, `harnesses`, `paths`, `doctor [pi]`, `setup pi --sync-packages`, `update [--check]`, and `uninstall [--remove-runtimes]`.
- Built releases embed version, commit, target, build kind, service origin, and the exact Pi version from `pi-version.json`. Production builds require a validated HTTPS `AXON_SERVICE_ORIGIN` base URL at build time (an optional mount such as `/axon` is preserved; no trailing slash); release clients use that embedded origin, not an ambient runtime update-server override. Source development can use a loopback HTTP origin. Release builds use ESM bytecode, external source maps, and disabled compiled `.env`/bunfig autoload.

Before ordinary Pi and setup/doctor/paths/harnesses work, a missing saved Axon session triggers interactive browser onboarding. Missing-session scripted/CI/offline runs fail with login guidance before provisioning. Help/auth/update/uninstall and Pi administrative commands are exempt; existing local sessions avoid onboarding network work.

## Pi behavior shipped with the CLI

- Pi is installed on demand from Pi's exact-version release metadata and validated lockfile into `${AXON_HOME}/pi-runtime/<version>` using `npm ci`. The launcher verifies the installed package and executable, uses **only** that managed Pi (never `pi` from `PATH`), and does not alter shell profiles or the user's global Pi. Offline launches and `doctor` do not install. `AXON_PI_BIN` is rejected; a different `AXON_PI_VERSION` is permitted only in source runs, not compiled builds. `axon pi update`, including `--extensions`, is blocked; a new reviewed CLI release changes the embedded pin.
- Pi settings/auth/packages and sessions live under `${AXON_HOME}/pi` and `${AXON_HOME}/pi/sessions`, not `~/.pi/agent`. Pi version checks and ambient provider API keys are disabled/removed for the child; LiteLLM and supporting cloud/proxy variables remain available. Launcher controls are stripped from the child environment, and debug launch previews are redacted.
- Axon-owned extensions, skills, prompts, and themes are embedded and checksum-verified under content-addressed `${AXON_HOME}/runtime/<version>-<hash>/pi`. Ordinary Pi sessions reference immutable resource paths through explicit flags. The bundled organization telemetry extension has its dependencies prebundled; export is inert without OTLP configuration. Accepted backend telemetry enablement has no local opt-out; explicit offline disables export. See [telemetry data policy](../src/harnesses/pi/telemetry/docs/data-policy.md).
- Required community packages follow embedded `exact`, `minimum`, or `floating` policies. Reconciliation uses a lock and local installed metadata; healthy warm launches do not query a package registry. An exact migration can fall back to a verified non-revoked last-known-good version. Interactive online sessions can install/repair requirements; non-interactive, print, JSON/RPC, piped, CI, and offline launches do not perform package-install network work and instead direct users to `axon setup pi --sync-packages` when repair is needed. Administration commands are forwarded without injected resource flags. See [package provisioning](plans/pi-package-provisioning.md).
- Authenticated online non-administrative Pi launches (including scripted modes) consume `/api/v1/cli/config` telemetry preferences best-effort, bounded to 700 ms and 16 KiB with no config disk cache. Remote collector/protocol/sampling/interval settings take priority over the environment, except explicit offline mode. Backend enablement also wins over local disablement for the extension and launcher product events through shutdown. Inherited exporter headers/TLS identity overrides are cleared for a config-managed collector. Errors preserve environment fallback and never block Pi. See [client configuration](plans/cli-client-config.md).
- Interactive online Pi startup performs a best-effort organization MCP catalog sync, limited to 700 ms and locally throttled (six hours after success, fifteen minutes after failure). It only appends missing servers to `~/.config/mcp/mcp.json`, forcing new entries to `disabled: true`; existing entries and user choices are preserved. Unavailable/invalid catalog data must not prevent Pi launch. Explicit `setup pi --sync-packages` forces a sync. This endpoint is **not** release policy.

## Release authority and trust

The current release source of truth is the backend's `CLI_RELEASES.VERSIONS` (immutable version-to-S3-key and two SHA-256 hashes) plus its single `CLI_RELEASES.LATEST_VERSION` pointer. The public `/install.sh` is rendered from `apps/cli/install.sh`; `/api/v1/cli/releases/latest/VERSION` selects a version, `/<version>/checksums.txt` supplies hashes, and `/<version>/axon-darwin-arm64.gz` redirects to a short-lived signed CloudFront download backed by private S3. A secret-protected backend presigned PUT is used **only** for manual publication. Do not put upload secrets, CloudFront signing keys, or AWS credentials in the binary or installer.

The archive and decompressed binary are both SHA-256 checked, and the executable's code signature and reported `--version` are checked before activation. The current signature is **ad-hoc**, not Developer ID/notarized. Checksums supplied by the same backend as the URL detect corruption but do **not** independently authenticate a compromised backend. There is no independently signed manifest, cohort/percentage rollout, mandatory minimum-version gate, or CLI rollback/hold command. A global latest-pointer change offers a newer release to all eligible managed clients; it does not downgrade those already updated.

## Publish a release (manual, native macOS arm64)

1. Update the CLI package version and, if changing Pi, `pi-version.json` plus the matching Pi development dependencies/lockfile. Run root and app checks/tests; run native installer/update smoke tests on Apple Silicon. Bitbucket CI checks the monorepo but does not build the macOS binary or publish. The retained GitHub Actions files are not this release channel. Git tags, if used, are `cli-<semver>`; there is no required GitHub Release.
2. From `apps/cli`, set `RELEASE_VERSION` (matching `package.json`), full `BUILD_COMMIT`, and production HTTPS `AXON_SERVICE_ORIGIN`; run `bun run release:prepare-s3`. It compiles, checks arm64, ad-hoc signs and probes the binary, creates a reproducible gzip, and writes local `release/` metadata, checksums, version, configuration snippet, and source map. Do not publish the map with the archive by default.
3. Add the generated `release/cli-release-config.json` version entry to the backend's ignored `config.json` under `CLI_RELEASES.VERSIONS` and restart it. Leave `LATEST_VERSION` unchanged (or empty for the first release). Configure the private S3/CloudFront credentials and upload auth as described in the backend README; verify the exact-version checksums endpoint. Never overwrite a published version key.
4. Set `CLI_UPLOAD_AUTH_KEY` privately and run `bun run release:publish-s3` from `apps/cli`. It compares both backend hashes, requests an immutable presigned PUT, uploads the archive, then re-downloads through CloudFront and verifies its hash. If the PUT succeeds but CDN verification fails, **do not repeat the PUT**: wait for cached 404s to expire and verify the existing object manually before promotion.
5. Set `CLI_RELEASES.LATEST_VERSION` to the verified version, restart the backend, and check `latest/VERSION`, public `/install.sh`, and `axon update --check` from a previous managed release. Keep earlier exact-version entries/objects for existing installations. Promotion is global; pilot using a separate environment or explicit exact-version testing before moving production latest.

## Installation and update handling

- The installer downloads to the managed `bin` filesystem, checks compressed/decompressed hashes, code signature, and version, then activates the binary. It keeps a previous copy as `bin/axon.prev`, prints PATH guidance, and never writes `/usr/local/bin`. A browser-downloaded, quarantined ad-hoc binary may be blocked by Gatekeeper; do not disable Gatekeeper globally. See [installation guidance](../README.md#installation).
- `axon update --check` fetches latest metadata and reports whether a newer version exists; it does not replace the binary. `axon update` explicitly downloads, verifies, and atomically installs a newer release, preserving `axon.prev`. Neither command downgrades. CLI self-update requires a supported release binary; mutation checks that the running executable is the managed inode, that managed paths are not symlinks, and that home/bin ownership and privacy are safe. A copy on an unrelated path cannot self-update. Update failures leave the current installation usable and return launcher update status `124`.
- After a launched Pi process exits, a **best-effort detached** worker is scheduled only for a binary invocation with TTY stdin/stdout, no truthy `CI`, and `AXON_NO_UPDATE` not exactly `1`. It uses `locks/update.lock`, records the next check in `update.json`, retries one hour after failure and checks again after 24 hours on success. It fetches and **installs** a verified newer release immediately for the **next** invocation; it does not merely stage it for a later swap. It is silent, cannot change the completed Pi exit status, and ordinary startup makes no synchronous binary-update request. Explicit `axon update` still works when background updates are disabled. Note: the worker does not currently inspect Pi's `--offline`/`PI_OFFLINE` flags, and its `CI` check is based on presence/truthiness rather than the Pi launch classifier's parsed boolean.
- `axon uninstall` requires the running managed executable and removes the live and `.prev` binaries, preserving Pi settings/auth/sessions and cached runtimes by default. `--remove-runtimes` additionally removes the cached Axon resource and Pi runtime trees; it does not delete user data.

## Verification and recovery

- Before publishing: `bun run check` and `bun test` from `apps/cli` (plus workspace checks), `bun run release:prepare-s3` and a native smoke run. Installer and release tests live in `apps/cli/tests/installer/`, `update.test.ts`, and `release-contract.test.ts`. Backend release routes have tests under `apps/backend/tests/test_cli_releases.py` and `test_install.py`.
- On a broken local setup, run `axon doctor pi` and `axon paths`. For missing pinned Pi or required packages while online, run `axon setup pi --sync-packages`. An offline missing runtime/package cannot be repaired silently. For binary update failures, keep using the installed version and retry explicit `axon update` after checking connectivity and managed-home permissions.
- If a published release is bad, stop offering it by restoring `LATEST_VERSION` to a previously verified version, then investigate and publish a fixed **new version**. This prevents new upgrades but does not roll back upgraded clients; `axon.prev` is retained as a recovery artifact, **not** an implemented rollback command. Keep the prior version's backend entry and S3 object accessible.

## Not shipped / separate future decisions

Independent manifest signatures and replay protection; percentage/cohort rollouts and channels; cached `minSupported` gates, mandatory foreground re-exec, and rollback holds; Developer ID signing/notarization; broader platform support; and a complete native PTY/process-group compatibility suite. Do not describe these as active protections or put their old proposed state/commands into the current release procedure. See the [controlled-rollout proposal](plans/controlled-rollout-versioning-updates.md) for future work.
